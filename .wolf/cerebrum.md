## Key Learnings

- **Project:** music-hub
- **Description:** 跨平台音乐播放列表管理器和启动器，支持网易云音乐、QQ音乐和哔哩哔哩。
- **App version is generated from git** at build time: `app/build.gradle.kts` reads `git describe --tags --always --dirty` for `versionName` and `git rev-list --count HEAD` for `versionCode`. Anything that wants to display the version must read it from `PackageManager.getPackageInfo()` at runtime — never hardcode it. (BuildConfig generation is not enabled, so use PackageInfo, not BuildConfig.VERSION_NAME.)
- **Landing-site brand name lives in 4 places**: (a) `site/index.html` `<title>` tag, (b) `site/index.html` hero `<h1 data-i18n="heroTitle">`, (c) `site/src/main.js` `heroTitle` keys for both `zh` and `en` languages (the JS overwrites the HTML fallback on load), (d) `android-app/app/src/main/res/values/strings.xml` `app_name` / `app_name_cn` / `floating_window_title`. All four must move together when renaming. **Current canonical pair is Tutti / 管乐** (decided 2026-05-17, replacing the earlier "Music Hub / 音乐枢纽" and the still-earlier "音乐中心"). The CLAUDE.md / README.md / fragment_setup.xml still reference older names — update on next code touch, not pre-emptively. Anatomy.md auto-syncs site title.
- **Name origin documented on the page**: A dedicated `name-section` between hero and positioning explains "管乐" (Chinese collective for wind instruments) and "Tutti" (Italian musical term for "everyone plays together"). i18n keys: `nameEyebrow`, `nameTitle`, `nameCopy1`, `nameCopy2`, `nameAside`. Keep this section if you rename — but update the etymology to the new pair, since the section is currently tightly bound to the 管乐/Tutti choice.
- **Site copy uses spaces around the Chinese brand**: e.g., "管乐 不播放、不下载..." rather than "管乐不播放...". The space disambiguates the brand from the literal Chinese meaning of "管乐" (wind instruments). When adding new copy that mentions the brand, follow this convention.
- **Internal identifiers were NOT renamed** when the brand changed: `./downloads/music-hub.apk` (filename), `localStorage.getItem('music-hub-language')` (storage key). Renaming the APK would require updating the Cloudflare build script and the metadata.json schema; renaming the storage key would orphan existing user-language preferences. Leave both as-is unless the migration cost is justified.
- **Site i18n pattern**: every translatable node has `data-i18n="someKey"` plus a Chinese fallback in the HTML. `site/src/main.js` defines `translations.zh` and `translations.en` dictionaries; `applyLanguage()` swaps `node.textContent` on load. HTML fallback is only visible if JS fails, so the JS dictionary is the source of truth for live content. Keep HTML fallbacks loosely in sync to avoid stale-looking source.
- **CSS line-wrapping for mixed CJK + English**: use `overflow-wrap: break-word` (not `anywhere`) and `text-wrap: balance` on headings. `overflow-wrap: anywhere` and `line-break: anywhere` break mid-word for English titles and look "strange". For inline `<code>` with long technical identifiers, use `word-break: break-word` so they wrap at sensible points without breaking the surrounding text.
- **Permission tiers (必需 / 推荐 / 可选) are canonicalized in `fragment_setup.xml`** — that XML is the source of truth for what's required vs optional. The landing site mirrors this with three matching badges. When adding a new permission, decide its tier in the Setup fragment first, then propagate to the site. Current tier assignments: **必需** = SYSTEM_ALERT_WINDOW + POST_NOTIFICATIONS; **推荐** = NotificationListenerService + PlayerAccessibilityService (QQ Music) + WRITE_SETTINGS (NetEase landscape) + PACKAGE_USAGE_STATS; **可选** = FreeformResizeAccessibilityService + Shizuku.
- **NetEase landscape workaround is foreground-mode only**: `DeepLinkLauncher.launchForeground` runs the rotation hack (force portrait → CLEAR_TASK → wait for STATE_PLAYING → restore auto-rotation, gated by `landscapeWorkaroundActive`). `launchBackground` deliberately skips all foreground workarounds (rotation, a11y tap, CLEAR_TASK) because freeform windows sidestep the problem — the music app is small enough that landscape player never gets invoked. When documenting limitations, attribute the rotation hack to foreground mode specifically, not the app generally.
- **All four platforms support `fetchPlaylistSongs` for auto-sync** (`NetEasePlatform`, `QQMusicPlatform`, `KugouPlatform`, `BilibiliPlatform`). `PlaylistSyncEngine.fetchSourceSongs` dispatches through `LinkParser.getHandler(platform)`, so any new platform handler that implements `fetchPlaylistSongs` automatically joins the sync rotation. **Do not document sync as "partially supported"** — that copy was stale.
- **Kugou public playlist API really does reject unauthenticated requests** (verified in `KugouPlatform.fetchPlaylistSongs` comments and the actual implementation): `m3ws.kugou.com/share/list`, `m.kugou.com/plist/list`, `wwwapi.kugou.com/v1/playlist/list_info` all return "No Action Found" or 404 without auth cookies. The working path is scraping `window.$output` JSON from the SSR'd share page at `https://m.kugou.com/songlist/gcid_<gcid>/`. So "needs login to fetch playlists" is accurate — the SSR fallback is what makes the feature work for unauthenticated users.
- **Kugou is the *only* platform whose internal endpoints reject unauthenticated requests**. None of the four platforms publish officially documented third-party playlist APIs — we use the internal endpoints each platform's own web/app client calls (NeteaseCloudMusicApi-style reverse engineering). The difference: NetEase `fetchPlaylistSongsV3` works with placeholder cookies for public playlists ("v3 API - works without login for public playlists"); QQ Music `fetchPlaylistSongs` chain (V1WithPagination → V2 → Web) doesn't set a Cookie header at all; Bilibili uses public `api.bilibili.com/x/v3/fav/resource/list`. Kugou's equivalents all return "No Action Found"/4xx without auth. When documenting this in user-facing copy, **don't call NetEase/QQ/Bilibili APIs "official" or "public"** — they're internal endpoints that happen to allow unauthenticated access. Auth cookies only matter for personalized features (`fetchDailyRecommendations`).
- **NetEase landscape: distinguish "separate landscape Activity" from "doesn't support landscape launch"**. NetEase has a *separate* `PlayerLandscapeActivity` launched by an `OrientationEventListener` inside `PlayerActivity` — it fires only on a *fresh* portrait→landscape transition. Other platforms don't have separate landscape Activities; they re-layout the same Activity via standard `onConfigurationChanged` callbacks. So "other platforms support landscape launch directly" is a wrong framing — the right framing is "other platforms handle rotation in-place inside the same Activity, no separate landscape Activity to wake up." This matters for the WRITE_SETTINGS permission explanation.
- **What FreeformResizeAccessibilityService actually does** (and what it doesn't): The service listens to `TYPE_WINDOWS_CHANGED` events on the 4 music apps and calls `ShizukuLauncher.triggerResize(pkg)` whenever HyperOS pulls a freeform window back on-screen (gesture nav, recents transitions). **It does NOT eliminate the brief window flash at song change** — that flash is a fixed timing gap between `am start --windowingMode 5` creating the task at HyperOS's default centered bounds and `am task resize` shrinking it (mentioned in the 2026-05-12 do-not-repeat). The two are independent issues — the accessibility service is about ongoing window-position maintenance, not creation-time invisibility. Don't describe its purpose as "prevent flash on song change."
- **QQ Music has no deep link that lands on the player page** (only the home screen or a mini card). The PlayerAccessibilityService taps the mini-player bar to switch to the full player; 16 retries × 500ms = ~8s max wait, with occasional fallback to the home screen. Whenever describing the QQ-Music permission requirement, this is the *reason* — the original "auto-tap mini player" description doesn't explain why we need such a service at all.
- **NetEase landscape hack: why it's only NetEase**. NetEase's `PlayerLandscapeActivity` is launched by an `OrientationEventListener` inside `PlayerActivity` that fires only on a *fresh* portrait→landscape transition — it doesn't fire when the device is already in landscape at activity-start time. Other platforms' players are landscape-launch-aware via the standard Configuration mechanism, so they don't need the rotation toggle. When documenting the WRITE_SETTINGS permission requirement, this is the *reason* — generic "rotation workaround" copy hides the platform-specific nature.
- **QQ Music's obfuscated UI IDs churn every release** and the mini-player layout shifts vertically with each redesign. `PlayerAccessibilityService` previously hardcoded a "magic" fallback click at `(554, 2117)` when ID-based lookups failed — that's actively dangerous on the singer-detail page (the landing page for many `playSonglist` deep links) where the song-track RecyclerView's last visible row sits at `[0,1976][1080,2144]` and is clickable, so the fallback would tap a song row → wrong song plays → title mismatch → skip. **The robust path is content-desc detection**: QQ Music's mini-player ImageViews carry stable Chinese accessibility labels (`歌曲队列` / `播放` / `暂停`) that survive ID churn. Find a marker near the bottom, then look for a wide clickable element on the same row to its LEFT (the song-info area). Never rely on hardcoded screen coordinates for cross-app taps — give up cleanly instead.

## Key Learnings

- **Fragment coroutine pattern**: Use `viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED)` inside any `viewLifecycleOwner.lifecycleScope.launch` block that collects from a StateFlow/Flow and accesses `binding`. Plain `collectLatest` has a race window where a final emission can fire after `onDestroyView()`. This matters especially when fragments are pushed off-screen immediately (e.g., first-run navigation).
- **First-run onboarding**: Setup screen (SetupFragment) is navigated to from MainActivity.onCreate() via `navController.navigate(R.id.nav_setup)` if `musichub_prefs.setup_complete` SharedPreferences flag is false. Covers POST_NOTIFICATIONS, SYSTEM_ALERT_WINDOW, notification listener, accessibility. SYSTEM_ALERT_WINDOW is the key permission that suppresses the "app wants to open QQ Music?" Android background activity launch dialog.
- **Launch modes (DeepLinkLauncher)**: Two modes selected via `launch_mode` ListPreference (default `background`). `launchBackground` uses `ActivityOptions.setLaunchBounds(tinyCornerRect)` + reflective `setLaunchWindowingMode(5)` (WINDOWING_MODE_FREEFORM) to start the music app in a small floating window — no rotation hack, no a11y mini-player tap, no CLEAR_TASK. `launchForeground` is the legacy path with all those workarounds. Locked-screen path is shared by both modes (freeform doesn't render under keyguard). Requires `enable_freeform_support=1` on the device for background mode to actually open as a floating window.
- **Kugou API quirks (KugouPlatform.kt)**:
  - **Songs are identified by 32-char hex content hash**, not numeric ID. Always lowercase the hash on parse — Kugou URLs sometimes uppercase it but the API is case-sensitive lowercase.
  - **Deep link must be `https://m.kugou.com/mixsong/<short-id>.html`** (the per-song share URL embedded as `_song_url` in the songlist data) with `setPackage("com.kugou.android")`. Two formats that DO NOT work:
    1. `kugou://start.weixin?action=songinfo&hash=<hash>` — Kugou's `start.weixin` entry expects a URL-encoded JSON payload (`{cmd, type, action, jsonStr, openBIData}`), NOT key=value query params. With the wrong shape Kugou silently opens some default song with strange info.
    2. `https://m.kugou.com/song/?hash=<HASH>` — Kugou's CDN returns "No Action Found!" (HTTP 200) without proper signed params; same for `https://m.kugou.com/song/<hash>.html`.
  - **Songlist (gcid) data**: All needed data is server-side-rendered into the share page itself at `https://m.kugou.com/songlist/gcid_<gcid>/` as `window.$output = {encode_gic, info:{listinfo:{name,pic,count}, songs:[...]}}`. The public API endpoints (`m3ws.kugou.com/share/list`, `m.kugou.com/plist/list/<gcid>`, `wwwapi.kugou.com/v1/playlist/list_info`) all return errors without auth. Parse the embedded JSON by locating `window.$output =` and bracket-balancing the object literal.
  - **Each song in `info.songs[]` has a `_song_url`** — that's the only reliable deep link.
  - **`name` field is `"Artist - Title"`** — split on first ` - ` to separate. Falls back to `singerinfo[].name` joined with `、` for artist.
  - **Song metadata endpoint**: `https://mobilecdnbj.kugou.com/api/v3/song/info?hash=<hash>` — needs `Referer: https://m.kugou.com/` header. Response: `{status: 1, data: {songname, singername, album_name, image, ...}}`. `status != 1` ⇒ unavailable. Image URLs contain `{size}` placeholder — replace with `120` or `400`.
  - **Kugou cycles current-lyric lines through the MediaSession `title` metadata** (词：方杰, 曲：雷颂德, lyric lines, etc.) — same behavior as NetEase. Any title-based verification (e.g. `PlaybackService.schedulePlaybackTimeout`'s "wrong song playing" check) MUST exempt Kugou alongside NetEase or it fires a spurious skip ~1-2s into every Kugou song.
  - **`platformSongId` is the bare lowercase hash** — no prefix like Bilibili uses (`video:`/`audio:`). Bilibili's prefix pattern doesn't need to extend to Kugou because Kugou only handles one content type (songs).
- **Shizuku `am start` for HTTPS deep links MUST include `-p <package>`.** `am start --windowingMode 5 -a android.intent.action.VIEW -d <url>` on its own goes through Android's standard HTTPS intent resolver, which can route `m.kugou.com` URLs to the browser instead of `com.kugou.android` (verified on HyperOS — Kugou was opening the browser inside the freeform window before this fix). NetEase/QQ Music/Bilibili happened to work because `orpheus://`, `qqmusic://`, `bilibili://` are uniquely claimed schemes — for them `-p` is redundant but harmless. `ShizukuLauncher.launchFreeform` now derives the target package via the existing `packageForDeepLink(deepLink)` mapping and conditionally appends `-p <package>` between `-d` and `-f`. Any future platform that uses HTTPS deep links (not a unique custom scheme) MUST be registered in `packageForDeepLink` or freeform launches will silently route to the wrong app.

[2026-06-02] **Do NOT suppress the same-platform QQ "third song" leak by pausing QQ (pause()+stop() pulses or a reactive title-gated window). It caused a DOUBLE-PLAY regression.** Unlike NetEase (which uses CLEAR_TASK, so pausing its MediaController doesn't disturb the fresh PlayerActivity), QQ Music receives same-platform deep links via `onNewIntent` on its EXISTING session. Sending `pause()+stop()` to QQ's controller during/after the `playSonglist` deep link FIGHTS QQ's own load of the target — empirically delayed the target ("3/8") from its ~15:44:03 launch to its actual STATE_PLAYING at 15:44:15 (~12s). If the user does a second switch (QQ→NetEase) in that gap, the cross-platform pin disarms when the NEW target (NetEase) plays (~15:44:12), and then QQ's delayed target starts UNGUARDED (~15:44:15) → QQ + NetEase audible simultaneously. Reverted the whole `samePlatformQQPause` / `pauseQQIfNotTarget` / `armSamePlatformQQPause` approach (bug-183 → bug-185). Constraints that make this leak hard: (1) STREAM_MUSIC mute is BANNED by the user — QQ/NetEase pop a "音量过低 / volume too low" notification (this is also why the bug-174 muteStreamForSwitch bridge is gone). (2) pausing QQ breaks its same-app deep-link load (this entry). (3) Tutti can't control QQ's internal queue. NET: treat the brief QQ same-platform third-song leak as a KNOWN LIMITATION unless a non-pause, non-mute mechanism is found. Root double-play enabler is also a latent pre-existing bug: the cross-platform pin disarms on TARGET STATE_PLAYING but does NOT guard a LATE-STARTING old app (bug-174's "defense-free tail window") — fix that separately if pursuing QQ suppression again.

[2026-05-29] **NetEase landscape: STATE_PLAYING is NOT a reliable proxy for "PlayerActivity's OrientationEventListener has registered while still portrait".** The landscape workaround restores auto-rotation (ACCELEROMETER_ROTATION=1) when NetEase reports its first armed STATE_PLAYING, expecting the resulting portrait→landscape edge to wake NetEase's listener into launching PlayerLandscapeActivity. But NetEase's audio engine (STATE_PLAYING) and its UI-thread listener registration are NOT strictly ordered — restoring rotation INLINE on STATE_PLAYING intermittently won the race, rotated the system to landscape before the listener existed, and the listener then registered already-landscape (no transition → portrait player). Fix (`DeepLinkLauncher.kt`): added `ROTATION_RESTORE_SETTLE_MS=900L` — postDelayed the restore so the UI has time to arm its listener while still portrait. **When touching the landscape restore timing, never assume STATE_PLAYING == "player UI ready"; it only means "audio engine ready", which can precede the listener.** Also added a zero-write diagnostic confirm-log (`ROTATION_CONFIRM_MS=700L`) that warns if the display is STILL PORTRAIT after restore (the rank-2 accelerometer-hysteresis residual). See bug-178.

[2026-05-06] When removing imports from a fragment, grep the *entire* file for all usages before deleting — not just the deleted methods. `Toast` was used in `observeData()` but the import was removed because it only appeared in the deleted `setupPermissionButtons`/`updatePermissionStatus` methods.

[2026-05-07] Fragment `collectLatest` coroutines crash if they access `binding` after navigation pushes the fragment off-screen. Always use `repeatOnLifecycle(STARTED)` to gate Flow collectors in Fragments.

[2026-05-08] **APK reinstalls revoke Shizuku permission silently.** Music Hub's `ShizukuLauncher.checkSelfPermission()` returns `PERMISSION_DENIED` after every reinstall until the user re-grants in Music Hub Settings → 启动模式 → Shizuku 授权. When the grant is missing, `launchBackground()` falls back to a regular Intent launch — which goes fullscreen because `setLaunchWindowingMode(5)` requires `MANAGE_ACTIVITY_TASKS` and is stripped for non-system callers. Symptom from the user's perspective: cold-launching any music app jumps to fullscreen instead of freeform sliver. Added a `Toast` in `launchBackground` that explains the cause when Shizuku status is not `READY`, so the silent regression is now visible.

[2026-05-10] **Don't add `FLAG_ACTIVITY_SINGLE_TOP` (0x20000000) to the `am start --windowingMode 5` launch.** SINGLE_TOP delivers via `onNewIntent` to the existing top activity instead of creating a new one — and the existing activity keeps its current windowing mode, fully bypassing the `--windowingMode 5` hint. Net effect: a previously-fullscreen music app stays fullscreen on song switch, breaking the whole freeform/off-screen UX. Use only `NEW_TASK | NO_ANIMATION` (0x10010000) plus `--no-window-animation`.

[2026-05-09] **HyperOS draws freeform window chrome on a separate system surface** that is *not* sized down by `am task resize`. Even with task bounds at 10×10, HyperOS renders a ~150×150 white frame (header bar + drag handle area) around the task on a system-rendered surface that we have no control over. Verified via screenshot: 10×10 task bounds still showed a visibly large white square behind the floating ball. The chrome size is HyperOS's enforced minimum and ignores our small bounds. Workaround: push task bounds *fully off-screen* (e.g., `left = screenW + 50`) so the chrome surface is also drawn off-screen — music keeps playing because the task is still freeform-visible-and-active, but nothing is rendered in the visible viewport.

(My earlier hypothesis that small bounds auto-converted to a "tiny floating ball" was wrong. HyperOS's actual native tiny-ball state requires the drag-to-edge gesture and is a separate sidebar overlay rendered by `miui_multi_sence`.) User preference is the tiny-ball mode (it actually doubles as a sidebar overlay covered by Music Hub's own SYSTEM_ALERT_WINDOW ball). Home-swipe gestures auto-expand the task to HyperOS's enforced minimum (~1.5 cm) breaking the tiny-ball mode; the watchdog re-shrinks to 60×60 to re-engage it. Use 400 ms watchdog period — slower felt visibly broken, faster wastes IPC.

[2026-05-09] **QQ Music creates a new task per deep-link launch** (unlike NetEase which reuses one). Old tasks linger as invisible freeform tasks for some time. Caching a single taskId from launch is wrong — by the time the watchdog fires, a different task may be the visible one. The dumpsys-grep `awk` for finding the right task **must** filter `visible=true` in addition to mode=freeform + Hist line containing the package, or you'll resize a hidden ghost task while the actually-visible one stays at QQ Music's default huge bounds. Watchdog should re-poll each tick rather than caching a taskId.

[2026-05-08] When resizing freeform tasks via `am task resize`, Bilibili's video-player chain (`IntentHandlerActivity` → `UnitedBizDetailsActivity`) **resets the task bounds back to HyperOS default** when the player finishes initializing, typically 2-4s after the first activity resumes. NetEase and QQ Music don't do this. Workaround: fire the resize twice — once when the task is first found, again after `Thread.sleep(3000)` once the player has stabilized. The second resize sticks. Verified via adb: a manual resize at t+0s gets reverted by t+5s; a manual resize at t+5s sticks indefinitely.

[2026-05-08] After an APK reinstall, HyperOS (and stock Android occasionally) leaves NotificationListenerService **unbound** even though the permission still shows enabled in Settings — `dumpsys notification | grep "Live notification listeners"` will be missing the entry. Symptom: `MediaMonitorService.getInstance()` returns null at runtime, MediaSession callbacks never fire, auto-advance always times out and skips. Fix: call `NotificationListenerService.requestRebind(ComponentName(ctx, MediaMonitorService::class.java))` from `Application.onCreate()` whenever the permission is granted. Adb workaround: `cmd notification disallow_listener com.musichub/.service.MediaMonitorService` then `allow_listener` re-binds it.

[2026-05-08] To find a freshly-launched task by package via `dumpsys activity activities`, do **not** grep `A=[0-9]*:<pkg>` — that's the task-affinity field, and apps like QQ Music declare a custom affinity (`A=10370:android.task.qqmusic`) that doesn't match the package name. Use `topResumedActivity.*<pkg>` instead — the line `topResumedActivity=ActivityRecord{... <pkg>/... tNNNN}` carries both the actual package and task id together, regardless of taskAffinity. Also: cold launches need polling, not a fixed sleep — `topResumedActivity` doesn't flip to the new app until its first activity fully resumes, which can take 1-3s on slow Chinese apps. Poll inside a single Shizuku-mediated shell loop (one binder IPC, ~30 × 200ms iterations) to keep both warm-launch latency and cold-launch reliability.

[2026-05-08] `ActivityOptions.setLaunchWindowingMode(WINDOWING_MODE_FREEFORM)` is a dead end for third-party apps. The reflection itself succeeds, but the framework's `ActivityStarter` silently strips the windowing-mode hint unless the caller holds `android.permission.MANAGE_ACTIVITY_TASKS`. That permission is `signature|privileged` and **not even `pm grant`-able from adb** ("not a changeable permission type"). Verified on HyperOS 3.0 (Xiaomi 24117RK2CC, OS3.0.302.0.WOKCNXM): `am start --windowingMode 5 -n com.netease.cloudmusic/.activity.IconChangeDefaultAlias` launches NetEase in freeform (`mWindowingMode=freeform` confirmed via `dumpsys activity activities`), but the equivalent call from our app does nothing — the hint is dropped. Path forward for freeform-style background launch is Shizuku (binds shell-UID privileges to apps via `dev.rikka.shizuku:api`) or accessibility-gesture automation; not a `setLaunchBounds`-only solution. `enable_freeform_support=1` and `force_resizable_activities=1` are necessary but not sufficient.

[2026-05-17] **Why accessibility silently disappears after the user "restarts" the app — AOSP force-stop behavior, not HyperOS-specific.** When any package gets force-stopped (`am force-stop`, HyperOS "Clear all" in Recents, HyperOS aggressive background-kill, Recents swipe-up close on HyperOS, manual force-stop from App info), AOSP's `ActivityManager` puts the package in `stopped=true` state. `AccessibilityManagerService` then excludes that package's services on its next `onSomePackagesChanged` sweep, which strips them from `Settings.Secure.enabled_accessibility_services` within ~50–200 ms. Re-launching the app clears `stopped=true` but the setting is NOT restored — the user has to dig back into Accessibility settings. **Verified empirically that this affects every app on the device, including official-store apps**: 钱迹 (`com.mutangtech.qianji`, `installerPackageName=com.xiaomi.market`) loses its SelectToSpeak service on `am force-stop` exactly the same way. Also verified the pre-background-mode version of Music Hub (`v0.0.0-14-gfcf40b2`, before `159c7f9`, with the narrowest possible single-package accessibility config) loses accessibility on force-stop too — so this was never "working" on any version. Things that do NOT trigger the disable: `am kill` (LMK-style), backgrounding via Home, APK reinstall, idle for 30+ seconds. **The previous theory that the trigger was `setComponentEnabledSetting` firing PACKAGE_CHANGED (notified_non_accessibility_category_services audit) was wrong** — that audit is a separate, much rarer category-classification mechanism; the actual everyday trigger is `stopped=true`. **Mitigation in code**: track grant in SharedPreferences any time we observe the service enabled, and on app launch use `ShizukuLauncher.restoreAccessibilityServices()` to re-write `Settings.Secure.enabled_accessibility_services` when the previously-granted service is missing. Writing that setting needs `WRITE_SECURE_SETTINGS` (signature-protected) which Shizuku grants to us via shell UID. Users without Shizuku still need to manually re-enable, but for Shizuku users this is silent and reliable. **Don't split the accessibility service into two** — an earlier attempt did this on the theory that a smaller-capability sibling could survive the rare category audit, but it traded marginal defense-in-depth for permanently doubling the manual-grant friction users without Shizuku see on every force-stop. Single combined PlayerAccessibilityService handles both QQ Music mini-player click (canRetrieveWindowContent + canPerformGestures on QQ Music events) and TYPE_WINDOWS_CHANGED freeform-resize for all four music apps; capability profile is the same whether the service is single or split since the QQ Music branch needs the full capabilities anyway.

[2026-05-16] **Bilibili video player auto-loops at end-of-content** without transitioning MediaSession state (stays PLAYING) and without changing metadata (same video). The position jumps from near-duration back to ~0. None of the three standard end-of-song detection paths in MediaMonitorService fire in this scenario: state-transition needs PLAYING→PAUSED/STOPPED (no state change on loop); metadata-change needs duration to change (same video doesn't); early-end poll needs `percentPlayed >= 99.8% AND remaining <= 3000ms` within a 1-second poll window (easy to miss). Workaround: detect the position-reset-while-PLAYING signal explicitly in `pollCurrentPosition` — if `maxPositionReached >= 95%` of duration AND `estimatedPosition < 10%` of duration AND state is still PLAYING AND not in manual control, treat as song-end. The 95% max-position guard prevents false-triggering on user-initiated seek-to-start (would require user to watch 95% then seek to start — vanishingly rare).

[2026-05-24] **Never fall back to hardcoded screen coordinates for cross-app accessibility taps.** `PlayerAccessibilityService.tryFallbackClick()` blindly tapped `(554, 2117)` whenever its ID-based mini-player lookups failed, on the theory that the mini-player is "usually there" on a 1080×2400 device. Two failure modes that made this dangerous: (1) QQ Music's obfuscated IDs `cxy`/`jrh`/`jro` are now `h58`/`h51` (changes per release), so ALL ID lookups returned empty and the fallback fired 3× per request (retries 1/2/3 before Strategy 4 "assume player open" kicked in at retry > 3). (2) The actual location of the mini-player shifted ~163 px lower than the hardcoded coordinate assumes, so `(554, 2117)` now sits inside a clickable song-list item on the singer-detail page where `playSonglist` deep links commonly land — each fallback tap played the wrong song, which `PlaybackService` then skipped via the title-mismatch path. Fix: detect the mini-player via stable content-desc strings (`歌曲队列` / `播放` / `暂停`) and clickable-ancestor walk; on failure, return without clicking. Strategy 4 ("assume player open" after retryCount > 3) provides the graceful exit. The lesson generalizes beyond QQ Music: any cross-app tap that can't verify the target structurally MUST give up rather than guess.

[2026-05-18] **Refinement of the 2026-05-16 "pause storm" entry below.** Only `armSamePlatformNetEasePause()` needs the `!isLandscapeForDoubleSend` gate, NOT the 6 scheduled `pausePackage()` calls. CLEAR_TASK does NOT destroy NetEase's internal persisted queue — verified empirically by a NetEase→NetEase landscape transition where the fresh `PlayerActivity` audibly played the queue's next track ("错的人 (Wrong Man)") for ~44 ms at position 2–46 ms before processing the deep link's `onNewIntent`. The 6 scheduled pauses (500/700/900/1100/1300/1500 ms post-launch) are direct pause+stop on NetEase's `MediaController.transportControls`; they don't touch `samePlatformNetEasePauseUntil` or `pendingPlaybackCallback`, so they can't short-circuit `firePendingPlaybackCallback` → `restoreAutoRotation`. Only the reactive `armSamePlatformNetEasePause()` has the early-`return` failure mode that breaks the landscape workaround — so its gate is still required. The 2026-05-16 entry below lumped both under "pause storm" and is overbroad; treat that entry's specific claims about the reactive pause as still valid, but disregard its "in landscape… pause storm is redundant" claim (the leak persists with or without CLEAR_TASK).

[2026-05-16] **The NetEase same-platform pause storm (armSamePlatformNetEasePause + 6 scheduled pauses in PlaybackService.doLaunchSong) MUST be gated on `!isLandscapeForDoubleSend`.** In landscape, the foreground landscape workaround uses CLEAR_TASK to destroy NetEase's queue (so there's no auto-advance to suppress — the pause storm is redundant). Worse, the 2500ms reactive-pause window armed by `armSamePlatformNetEasePause` can fire on the **target song's** first STATE_PLAYING (position ~0) inside MediaMonitorService.onPlaybackStateChanged. The reactive-pause branch `return`s early — skipping the `firePendingPlaybackCallback` block that's supposed to call `restoreAutoRotation`. Device stays portrait (ACCELEROMETER_ROTATION=0, USER_ROTATION=0), NetEase loads PlayerActivity (portrait) instead of PlayerLandscapeActivity. Only song 2+ is affected because `isSamePlatformNetEase` requires `lastLaunchedPlatform==NETEASE`. The original `beeb116` already gated its re-send block correctly with the same `!isLandscapeForDoubleSend` check — the later `6cef8fe` "audio bleed" commit added the pause-storm block but forgot to copy the gate. Any future per-platform workaround that runs alongside the landscape workaround should remember: MediaMonitorService's `firePendingPlaybackCallback` (which restores rotation) is fragile to early `return`s in onPlaybackStateChanged.

[2026-05-16] **HyperOS NotificationListenerService rebind: `requestRebind()` alone is unreliable — must toggle component enabled state first.** After APK reinstall or HyperOS killing Music Hub's process, the listener silently stays unbound (still appears granted in Settings, MediaMonitorService callbacks never fire, getPlaybackInfo() returns null, floating-window progress stuck at 0% while song title still renders from the DB). The Shizuku path (`cmd notification disallow_listener/allow_listener`) is fully reliable; the Java fallback needs `PackageManager.setComponentEnabledSetting(component, DISABLED, DONT_KILL_APP)` followed by `(ENABLED, DONT_KILL_APP)` *before* `NotificationListenerService.requestRebind(component)`. The disable+enable forces the system to drop and re-establish the binding. Verified end-to-end: force-stop → relaunch → log shows "Toggled component state and requested rebind" then "NotificationListener connected" within ~1s.

[2026-05-12] **`am start --windowingMode 5` always creates the freeform task at HyperOS's default centered bounds first (≈Rect(279,698,801,1778) on 1080×2400), THEN renders the activity — so even with NO_ANIMATION the user sees a visible flash before `am task resize` lands.** Two fixes, both already in `ShizukuLauncher.buildLaunchScript`:
  1. **Reuse path (warm)**: if an existing freeform task for the target package is already visible, deliver the deep link with plain `am start -a VIEW -d <url> -p <pkg>` (no `--windowingMode 5`). The intent goes through onNewIntent on the existing task and the task keeps its current bounds — **no new task created, zero flash**. Verified on Kugou (`launchMode=singleTop` MediaActivity) and NetEase. Resize-first inside the same script if the existing task drifted away from target bounds.
  2. **Cold path (first launch only)**: inline the poll-and-resize into the SAME shell script as the launch (`am start --windowingMode 5 ...; while ...; do INFO=$(findTaskInfo); ...; sleep 0.01; done; am task resize`). Cuts the flash window from ~180ms (Java thread + new Shizuku IPC for resize) to ~30-50ms (one binder IPC, 10ms polling). Output line `MODE=cold AM_EXIT=0 TID=... RESIZE_AT=NxN0ms` reports which polling iteration found the task.
  Key insight from the 2026-05-10 do-not-repeat: SINGLE_TOP fails when combined with `--windowingMode 5` because the existing activity keeps its old (fullscreen) mode. That earlier failure was on a fullscreen→freeform transition; we now intentionally rely on the same "existing task keeps its mode" behavior — but only when the existing mode is already freeform-off-screen. The check is "is there a visible freeform task for this package?" If yes → reuse safely; if no → cold path with the windowingMode hint.

[2026-05-29] **`MediaMonitorService.getInstance() != null` is NOT a valid "listener is bound" signal — gate the onResume rebind on a real `listenerConnected` flag.** `instance` is set in `onCreate` and only nulled in `onDestroy`; it SURVIVES a silent HyperOS listener unbind (`onListenerDisconnected` clears `activeControllers` + unregisters the session listener but leaves `instance` non-null). Commit `f2914bd` added `if (getInstance() != null) return` to `rebindMediaMonitorIfNeeded()` (to stop the Shizuku toggle bouncing `currentPlatformPackage` every 5-10s), but that early-return then masked the unbound-with-empty-controllers state forever — so a cross-platform switch found NO controller to pause and **two platforms bled audio simultaneously**. Fix: `@Volatile listenerConnected` set in `onListenerConnected`, cleared in `onListenerDisconnected`/`onDestroy`; gate the skip on `MediaMonitorService.isListenerConnected()` — it's a **companion** fun, call it statically on the class, NOT on a `getInstance()?.` instance (that fails to compile: "Unresolved reference"). Do NOT additionally require `activeControllers` non-empty: a freshly-connected listener with no music app running is legitimately empty, and that clause would re-introduce the every-5-10s toggle churn f2914bd fixed.

[2026-05-29] **The "mutes the music stream as a guaranteed fallback" claim in `armSamePlatformNetEasePause`'s doc-comment was a LIE.** The body only set `samePlatformNetEasePauseUntil` (a timestamp); it never touched STREAM_MUSIC. No mute fallback existed anywhere (`git log -S setStreamMute / adjustStreamVolume / ADJUST_MUTE` → zero in the pause path; only the FloatingWindowService volume slider + RemoteServer touch volume). Tutti also never requests audio focus. So pre-fix the ONLY cross-platform silencer was `transportControls.pause()+stop()`, which NetEase/QQ routinely ignore. A real mute bridge was added 2026-05-29 (`muteStreamForSwitch`/`unmuteStreamForSwitch`), **foreground-mode + cross-platform ONLY** — muting on the same-platform NetEase path would inherit the landscape early-`return` hazard from the 2026-05-16 entries.

[2026-05-29] **Cross-platform switch defenses (pin / re-pause / mute / force-stop) MUST be switch-scoped and torn down on user pause/stop — never a free-running invariant.** User requirement: when they pause, they may want to manually play another platform OR resume the old one, and Tutti must not fight them. Defenses arm only inside `pauseAllMedia` (a Tutti-initiated launch), disarm event-driven when the target plays (or a 10s timeout), and `togglePlayPause()`/`stop()` call `cancelCrossPlatformSwitch()` (clears the pin + unmutes). Do NOT implement a permanent "non-current platform must never play" rule — it would re-pause/kill apps the user deliberately started while Tutti is idle.

## Decision Log

<!-- Significant technical decisions with rationale. Why X was chosen over Y. -->

[2026-05-29] **Mode-aware cross-platform silencer chosen over a single mechanism.** The most reliable way to stop an uncooperative old app (NetEase/QQ ignore pause+stop) is to kill it, but only background mode carries Shizuku. So: background+Shizuku → `am force-stop` the old platform (reuse `ShizukuLauncher.purgeMusicAppTasks(exclude = musicAppPackages() - oldPkg)`, which purges only the old one); foreground / no-Shizuku → cross-platform-only `STREAM_MUSIC` mute bridge (unmute on target `STATE_PLAYING` / 10s safety / user pause). Both layered on L0 (keep the listener bound so controllers exist) + L1 (event-driven pin held until the target actually plays, instead of a blind 3s timer). REJECTED: a permanent "non-current platform must never play" invariant (fights a user who pauses then manually plays — their explicit requirement). REJECTED: reusing `pendingPlaybackCallback` for the pin disarm — it's single-slot and owned by the NetEase landscape `restoreAutoRotation` workaround; sharing it would lock the device in portrait. Honest ceiling: background mode is ~100% (old app killed); foreground reduces sustained bleed to brief blips since Android offers no per-app silencing without elevated privileges.
