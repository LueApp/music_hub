## Key Learnings

- **Project:** music-hub
- **Description:** 跨平台音乐播放列表管理器和启动器，支持网易云音乐、QQ音乐和哔哩哔哩。
- **App version is generated from git** at build time: `app/build.gradle.kts` reads `git describe --tags --always --dirty` for `versionName` and `git rev-list --count HEAD` for `versionCode`. Anything that wants to display the version must read it from `PackageManager.getPackageInfo()` at runtime — never hardcode it. (BuildConfig generation is not enabled, so use PackageInfo, not BuildConfig.VERSION_NAME.)

## Key Learnings

- **Fragment coroutine pattern**: Use `viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED)` inside any `viewLifecycleOwner.lifecycleScope.launch` block that collects from a StateFlow/Flow and accesses `binding`. Plain `collectLatest` has a race window where a final emission can fire after `onDestroyView()`. This matters especially when fragments are pushed off-screen immediately (e.g., first-run navigation).
- **First-run onboarding**: Setup screen (SetupFragment) is navigated to from MainActivity.onCreate() via `navController.navigate(R.id.nav_setup)` if `musichub_prefs.setup_complete` SharedPreferences flag is false. Covers POST_NOTIFICATIONS, SYSTEM_ALERT_WINDOW, notification listener, accessibility. SYSTEM_ALERT_WINDOW is the key permission that suppresses the "app wants to open QQ Music?" Android background activity launch dialog.
- **Launch modes (DeepLinkLauncher)**: Two modes selected via `launch_mode` ListPreference (default `background`). `launchBackground` uses `ActivityOptions.setLaunchBounds(tinyCornerRect)` + reflective `setLaunchWindowingMode(5)` (WINDOWING_MODE_FREEFORM) to start the music app in a small floating window — no rotation hack, no a11y mini-player tap, no CLEAR_TASK. `launchForeground` is the legacy path with all those workarounds. Locked-screen path is shared by both modes (freeform doesn't render under keyguard). Requires `enable_freeform_support=1` on the device for background mode to actually open as a floating window.
- **Kugou API quirks (KugouPlatform.kt)**:
  - **Songs are identified by 32-char hex content hash**, not numeric ID. Always lowercase the hash on parse — Kugou URLs sometimes uppercase it but the API is case-sensitive lowercase.
  - **Deep link must be `https://m.kugou.com/mixsong/<short-id>.html`** (the per-song share URL embedded as `_song_url` in the songlist data) with `setPackage("com.kugou.android")`. Two formats that DO NOT work:
    1. `kugou://start.weixin?action=songinfo&hash=<hash>` — Kugou's `start.weixin` entry expects a URL-encoded JSON payload (`{cmd, type, action, jsonStr, openBIData}`), NOT key=value query params. With the wrong shape Kugou silently opens some default song with strange info.
    2. `https://m.kugou.com/song/?hash=<HASH>` — Kugou's CDN returns "No Action Found!" (HTTP 200) without proper signed params; same for `https://m.kugou.com/song/<hash>.html`.
  - **Songlist (gcid) data**: All needed data is server-side-rendered into the share page itself at `https://m.kugou.com/songlist/gcid_<gcid>/` as `window.$output = {encode_gic, info:{listinfo:{name,pic,count}, songs:[...]}}`. The public API endpoints (`m3ws.kugou.com/share/list`, `m.kugou.com/plist/list/<gcid>`, `wwwapi.kugou.com/v1/playlist/list_info`) all return errors without auth. Parse the embedded JSON by locating `window.$output =` and bracket-balancing the object literal.
  - **Each song in `info.songs[]` has a `_song_url`** — that's the only reliable deep link.
  - **`name` field is `"Artist - Title"`** — split on first ` - ` to separate. Falls back to `singerinfo[].name` joined with `、` for artist.
  - **Song metadata endpoint**: `https://mobilecdnbj.kugou.com/api/v3/song/info?hash=<hash>` — needs `Referer: https://m.kugou.com/` header. Response: `{status: 1, data: {songname, singername, album_name, image, ...}}`. `status != 1` ⇒ unavailable. Image URLs contain `{size}` placeholder — replace with `120` or `400`.
  - **Kugou cycles current-lyric lines through the MediaSession `title` metadata** (词：方杰, 曲：雷颂德, lyric lines, etc.) — same behavior as NetEase. Any title-based verification (e.g. `PlaybackService.schedulePlaybackTimeout`'s "wrong song playing" check) MUST exempt Kugou alongside NetEase or it fires a spurious skip ~1-2s into every Kugou song.
  - **`platformSongId` is the bare lowercase hash** — no prefix like Bilibili uses (`video:`/`audio:`). Bilibili's prefix pattern doesn't need to extend to Kugou because Kugou only handles one content type (songs).
- **Shizuku `am start` for HTTPS deep links MUST include `-p <package>`.** `am start --windowingMode 5 -a android.intent.action.VIEW -d <url>` on its own goes through Android's standard HTTPS intent resolver, which can route `m.kugou.com` URLs to the browser instead of `com.kugou.android` (verified on HyperOS — Kugou was opening the browser inside the freeform window before this fix). NetEase/QQ Music/Bilibili happened to work because `orpheus://`, `qqmusic://`, `bilibili://` are uniquely claimed schemes — for them `-p` is redundant but harmless. `ShizukuLauncher.launchFreeform` now derives the target package via the existing `packageForDeepLink(deepLink)` mapping and conditionally appends `-p <package>` between `-d` and `-f`. Any future platform that uses HTTPS deep links (not a unique custom scheme) MUST be registered in `packageForDeepLink` or freeform launches will silently route to the wrong app.

[2026-05-06] When removing imports from a fragment, grep the *entire* file for all usages before deleting — not just the deleted methods. `Toast` was used in `observeData()` but the import was removed because it only appeared in the deleted `setupPermissionButtons`/`updatePermissionStatus` methods.

[2026-05-07] Fragment `collectLatest` coroutines crash if they access `binding` after navigation pushes the fragment off-screen. Always use `repeatOnLifecycle(STARTED)` to gate Flow collectors in Fragments.

[2026-05-08] **APK reinstalls revoke Shizuku permission silently.** Music Hub's `ShizukuLauncher.checkSelfPermission()` returns `PERMISSION_DENIED` after every reinstall until the user re-grants in Music Hub Settings → 启动模式 → Shizuku 授权. When the grant is missing, `launchBackground()` falls back to a regular Intent launch — which goes fullscreen because `setLaunchWindowingMode(5)` requires `MANAGE_ACTIVITY_TASKS` and is stripped for non-system callers. Symptom from the user's perspective: cold-launching any music app jumps to fullscreen instead of freeform sliver. Added a `Toast` in `launchBackground` that explains the cause when Shizuku status is not `READY`, so the silent regression is now visible.

[2026-05-10] **Don't add `FLAG_ACTIVITY_SINGLE_TOP` (0x20000000) to the `am start --windowingMode 5` launch.** SINGLE_TOP delivers via `onNewIntent` to the existing top activity instead of creating a new one — and the existing activity keeps its current windowing mode, fully bypassing the `--windowingMode 5` hint. Net effect: a previously-fullscreen music app stays fullscreen on song switch, breaking the whole freeform/off-screen UX. Use only `NEW_TASK | NO_ANIMATION` (0x10010000) plus `--no-window-animation`.

[2026-05-09] **HyperOS draws freeform window chrome on a separate system surface** that is *not* sized down by `am task resize`. Even with task bounds at 10×10, HyperOS renders a ~150×150 white frame (header bar + drag handle area) around the task on a system-rendered surface that we have no control over. Verified via screenshot: 10×10 task bounds still showed a visibly large white square behind the floating ball. The chrome size is HyperOS's enforced minimum and ignores our small bounds. Workaround: push task bounds *fully off-screen* (e.g., `left = screenW + 50`) so the chrome surface is also drawn off-screen — music keeps playing because the task is still freeform-visible-and-active, but nothing is rendered in the visible viewport.

(My earlier hypothesis that small bounds auto-converted to a "tiny floating ball" was wrong. HyperOS's actual native tiny-ball state requires the drag-to-edge gesture and is a separate sidebar overlay rendered by `miui_multi_sence`.) User preference is the tiny-ball mode (it actually doubles as a sidebar overlay covered by Music Hub's own SYSTEM_ALERT_WINDOW ball). Home-swipe gestures auto-expand the task to HyperOS's enforced minimum (~1.5 cm) breaking the tiny-ball mode; the watchdog re-shrinks to 60×60 to re-engage it. Use 400 ms watchdog period — slower felt visibly broken, faster wastes IPC.

[2026-05-09] **QQ Music creates a new task per deep-link launch** (unlike NetEase which reuses one). Old tasks linger as invisible freeform tasks for some time. Caching a single taskId from launch is wrong — by the time the watchdog fires, a different task may be the visible one. The dumpsys-grep `awk` for finding the right task **must** filter `visible=true` in addition to mode=freeform + Hist line containing the package, or you'll resize a hidden ghost task while the actually-visible one stays at QQ Music's default huge bounds. Watchdog should re-poll each tick rather than caching a taskId.

[2026-05-08] When resizing freeform tasks via `am task resize`, Bilibili's video-player chain (`IntentHandlerActivity` → `UnitedBizDetailsActivity`) **resets the task bounds back to HyperOS default** when the player finishes initializing, typically 2-4s after the first activity resumes. NetEase and QQ Music don't do this. Workaround: fire the resize twice — once when the task is first found, again after `Thread.sleep(3000)` once the player has stabilized. The second resize sticks. Verified via adb: a manual resize at t+0s gets reverted by t+5s; a manual resize at t+5s sticks indefinitely.

[2026-05-08] After an APK reinstall, HyperOS (and stock Android occasionally) leaves NotificationListenerService **unbound** even though the permission still shows enabled in Settings — `dumpsys notification | grep "Live notification listeners"` will be missing the entry. Symptom: `MediaMonitorService.getInstance()` returns null at runtime, MediaSession callbacks never fire, auto-advance always times out and skips. Fix: call `NotificationListenerService.requestRebind(ComponentName(ctx, MediaMonitorService::class.java))` from `Application.onCreate()` whenever the permission is granted. Adb workaround: `cmd notification disallow_listener com.musichub/.service.MediaMonitorService` then `allow_listener` re-binds it.

[2026-05-08] To find a freshly-launched task by package via `dumpsys activity activities`, do **not** grep `A=[0-9]*:<pkg>` — that's the task-affinity field, and apps like QQ Music declare a custom affinity (`A=10370:android.task.qqmusic`) that doesn't match the package name. Use `topResumedActivity.*<pkg>` instead — the line `topResumedActivity=ActivityRecord{... <pkg>/... tNNNN}` carries both the actual package and task id together, regardless of taskAffinity. Also: cold launches need polling, not a fixed sleep — `topResumedActivity` doesn't flip to the new app until its first activity fully resumes, which can take 1-3s on slow Chinese apps. Poll inside a single Shizuku-mediated shell loop (one binder IPC, ~30 × 200ms iterations) to keep both warm-launch latency and cold-launch reliability.

[2026-05-08] `ActivityOptions.setLaunchWindowingMode(WINDOWING_MODE_FREEFORM)` is a dead end for third-party apps. The reflection itself succeeds, but the framework's `ActivityStarter` silently strips the windowing-mode hint unless the caller holds `android.permission.MANAGE_ACTIVITY_TASKS`. That permission is `signature|privileged` and **not even `pm grant`-able from adb** ("not a changeable permission type"). Verified on HyperOS 3.0 (Xiaomi 24117RK2CC, OS3.0.302.0.WOKCNXM): `am start --windowingMode 5 -n com.netease.cloudmusic/.activity.IconChangeDefaultAlias` launches NetEase in freeform (`mWindowingMode=freeform` confirmed via `dumpsys activity activities`), but the equivalent call from our app does nothing — the hint is dropped. Path forward for freeform-style background launch is Shizuku (binds shell-UID privileges to apps via `dev.rikka.shizuku:api`) or accessibility-gesture automation; not a `setLaunchBounds`-only solution. `enable_freeform_support=1` and `force_resizable_activities=1` are necessary but not sufficient.

[2026-05-17] **HyperOS auto-disables sideloaded accessibility services with a "powerful + broadly scoped" profile — split the service to escape the audit.** `com.miui.securitycenter` / `com.lbe.security.miui` periodically classifies sideloaded accessibility services (`installerPackageName=null`) as "non-accessibility category" and silently disables them. The classification is tracked in `Settings.Secure.notified_non_accessibility_category_services` and surveys the *manifest XML* (not the runtime `serviceInfo` override). The trigger is a *combination*: `canRetrieveWindowContent=true` + `canPerformGestures=true` + `flagRetrieveInteractiveWindows` + chatty event types + low `notificationTimeout` + a `packageNames=` list covering multiple unrelated apps. Tightening `packageNames` to the 4 music apps moved the needle but didn't fully fix it — 4 unrelated apps + the full capability set is still enough for the audit to fire intermittently. **The working fix is to split the single service into two with separate manifest declarations:** (1) `PlayerAccessibilityService` keeps `canRetrieveWindowContent` + `canPerformGestures` (needed for the QQ Music mini-player click) but is scoped to `packageNames=[com.tencent.qqmusic]` only; event types narrowed to `typeWindowStateChanged|typeWindowContentChanged`; `flagRetrieveInteractiveWindows` removed. (2) `FreeformResizeAccessibilityService` (new) handles only `TYPE_WINDOWS_CHANGED` across the 4 music apps with `canRetrieveWindowContent=false` + `canPerformGestures=false` — clean profile, survives the audit even though it lists 4 packages. Each service has its own toggle in Setup screen and Settings > 权限. Split also limits blast radius: if HyperOS disables one, the other still works (QQ Music navigation vs background-mode resize are independent features). Important: runtime `serviceInfo` must mirror the manifest XML — a runtime that broadens scope beyond the manifest is dead anyway, and a runtime narrower than the manifest pays the audit cost without delivering the events.

[2026-05-16] **Bilibili video player auto-loops at end-of-content** without transitioning MediaSession state (stays PLAYING) and without changing metadata (same video). The position jumps from near-duration back to ~0. None of the three standard end-of-song detection paths in MediaMonitorService fire in this scenario: state-transition needs PLAYING→PAUSED/STOPPED (no state change on loop); metadata-change needs duration to change (same video doesn't); early-end poll needs `percentPlayed >= 99.8% AND remaining <= 3000ms` within a 1-second poll window (easy to miss). Workaround: detect the position-reset-while-PLAYING signal explicitly in `pollCurrentPosition` — if `maxPositionReached >= 95%` of duration AND `estimatedPosition < 10%` of duration AND state is still PLAYING AND not in manual control, treat as song-end. The 95% max-position guard prevents false-triggering on user-initiated seek-to-start (would require user to watch 95% then seek to start — vanishingly rare).

[2026-05-16] **The NetEase same-platform pause storm (armSamePlatformNetEasePause + 6 scheduled pauses in PlaybackService.doLaunchSong) MUST be gated on `!isLandscapeForDoubleSend`.** In landscape, the foreground landscape workaround uses CLEAR_TASK to destroy NetEase's queue (so there's no auto-advance to suppress — the pause storm is redundant). Worse, the 2500ms reactive-pause window armed by `armSamePlatformNetEasePause` can fire on the **target song's** first STATE_PLAYING (position ~0) inside MediaMonitorService.onPlaybackStateChanged. The reactive-pause branch `return`s early — skipping the `firePendingPlaybackCallback` block that's supposed to call `restoreAutoRotation`. Device stays portrait (ACCELEROMETER_ROTATION=0, USER_ROTATION=0), NetEase loads PlayerActivity (portrait) instead of PlayerLandscapeActivity. Only song 2+ is affected because `isSamePlatformNetEase` requires `lastLaunchedPlatform==NETEASE`. The original `beeb116` already gated its re-send block correctly with the same `!isLandscapeForDoubleSend` check — the later `6cef8fe` "audio bleed" commit added the pause-storm block but forgot to copy the gate. Any future per-platform workaround that runs alongside the landscape workaround should remember: MediaMonitorService's `firePendingPlaybackCallback` (which restores rotation) is fragile to early `return`s in onPlaybackStateChanged.

[2026-05-16] **HyperOS NotificationListenerService rebind: `requestRebind()` alone is unreliable — must toggle component enabled state first.** After APK reinstall or HyperOS killing Music Hub's process, the listener silently stays unbound (still appears granted in Settings, MediaMonitorService callbacks never fire, getPlaybackInfo() returns null, floating-window progress stuck at 0% while song title still renders from the DB). The Shizuku path (`cmd notification disallow_listener/allow_listener`) is fully reliable; the Java fallback needs `PackageManager.setComponentEnabledSetting(component, DISABLED, DONT_KILL_APP)` followed by `(ENABLED, DONT_KILL_APP)` *before* `NotificationListenerService.requestRebind(component)`. The disable+enable forces the system to drop and re-establish the binding. Verified end-to-end: force-stop → relaunch → log shows "Toggled component state and requested rebind" then "NotificationListener connected" within ~1s.

[2026-05-12] **`am start --windowingMode 5` always creates the freeform task at HyperOS's default centered bounds first (≈Rect(279,698,801,1778) on 1080×2400), THEN renders the activity — so even with NO_ANIMATION the user sees a visible flash before `am task resize` lands.** Two fixes, both already in `ShizukuLauncher.buildLaunchScript`:
  1. **Reuse path (warm)**: if an existing freeform task for the target package is already visible, deliver the deep link with plain `am start -a VIEW -d <url> -p <pkg>` (no `--windowingMode 5`). The intent goes through onNewIntent on the existing task and the task keeps its current bounds — **no new task created, zero flash**. Verified on Kugou (`launchMode=singleTop` MediaActivity) and NetEase. Resize-first inside the same script if the existing task drifted away from target bounds.
  2. **Cold path (first launch only)**: inline the poll-and-resize into the SAME shell script as the launch (`am start --windowingMode 5 ...; while ...; do INFO=$(findTaskInfo); ...; sleep 0.01; done; am task resize`). Cuts the flash window from ~180ms (Java thread + new Shizuku IPC for resize) to ~30-50ms (one binder IPC, 10ms polling). Output line `MODE=cold AM_EXIT=0 TID=... RESIZE_AT=NxN0ms` reports which polling iteration found the task.
  Key insight from the 2026-05-10 do-not-repeat: SINGLE_TOP fails when combined with `--windowingMode 5` because the existing activity keeps its old (fullscreen) mode. That earlier failure was on a fullscreen→freeform transition; we now intentionally rely on the same "existing task keeps its mode" behavior — but only when the existing mode is already freeform-off-screen. The check is "is there a visible freeform task for this package?" If yes → reuse safely; if no → cold path with the windowingMode hint.
