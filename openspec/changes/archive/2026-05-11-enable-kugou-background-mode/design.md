## Context

Background launch mode (`launch_mode=background`, the default) opens a song's native music app in a freeform window pushed off-screen, so the user keeps the Music Hub floating ball on top while the music app plays invisibly behind it. The mechanism is:

1. `DeepLinkLauncher.launchBackground()` is called by `PlaybackService` when a song should start.
2. It computes off-screen bounds (`computeBackgroundBounds`, anchored to the floating-ball Y position so the freeform window's chrome stays off-screen).
3. It calls `ShizukuLauncher.launchFreeform(context, deepLink, bounds, boundsProvider)`.
4. `ShizukuLauncher` shells out via Shizuku (shell-UID privileges):
   ```
   am start --windowingMode 5 -a android.intent.action.VIEW -d <deepLink> -f 0x10010000
   ```
   then asynchronously polls `dumpsys activity activities` for the new freeform task and runs `am task resize` to move it to the off-screen bounds, with a watchdog that re-resizes if HyperOS snaps the task back.
5. If Shizuku isn't ready, the launcher falls back to a regular `startActivity(intent)` with a freeform `ActivityOptions` bundle (and `setPackage(<music app>)`).

The three originally-supported platforms work because their deep links use custom URI schemes (`orpheus://`, `qqmusic://`, `bilibili://`) for which only the target music app has a matching intent-filter — `am start` always resolves the right app without a `-p` hint.

Kugou Music is the fourth platform (added recently) and is wired everywhere a platform branch is needed in background mode:
- `ShizukuLauncher.musicAppPackages()` includes `com.kugou.android` (so PlayerAccessibilityService listens for its window events).
- `ShizukuLauncher.packageForDeepLink()` maps `kugou://` / `kugou.com` URLs to `com.kugou.android`.
- `DeepLinkLauncher.launchBackground` fallback path calls `setPackage(KUGOU_PACKAGE)` for Kugou.
- `DeepLinkLauncher.launchForLockedScreen` calls `setPackage(KUGOU_PACKAGE)` for Kugou.
- `PlaybackService.schedulePlaybackTimeout` exempts Kugou (alongside NetEase) from the "wrong song" title check, since Kugou cycles current-lyric lines through MediaSession.title.

What's missing: Kugou's deep link is an HTTPS URL (`https://m.kugou.com/mixsong/<id>.html` or `https://m.kugou.com/song/?hash=<hash>`), so `am start -a VIEW -d <kugou-url>` (no `-p`) goes through Android's standard HTTPS intent-resolver. On the user's HyperOS device this resolves either to the system browser (running the Kugou web page) or to a disambiguation dialog — not to the Kugou app. The freeform window therefore opens the *wrong* foreground task and the resize watchdog never finds a `com.kugou.android` task to resize.

## Goals / Non-Goals

**Goals:**
- Under `launch_mode=background` with Shizuku ready, Kugou songs SHALL open in the Kugou app (`com.kugou.android`) inside an off-screen freeform window, just like NetEase / QQ Music / Bilibili.
- `am start` SHALL be constrained to the Kugou package when the deep link is a Kugou URL, so the resolver cannot route to a browser or another HTTPS handler.
- The change SHALL leave NetEase / QQ Music / Bilibili background-mode behavior bit-identical (custom-scheme deep links + an optional `-p <pkg>` arg → same target activity).
- The change SHALL preserve the existing fallback paths (Shizuku unavailable → regular `startActivity` with `setPackage`; locked screen → existing locked-screen Intent).

**Non-Goals:**
- Not modifying how Kugou deep links are generated by `KugouPlatform.generateDeepLink` or `KugouPlatform.fetchPlaylistSongs` — the HTTPS URLs stay as-is.
- Not introducing a new launch mode or new user setting — uses the existing background/foreground toggle.
- Not changing the off-screen bounds, the watchdog period, or the AccessibilityService's hooks — those are platform-agnostic and already correct.
- Not adding new Android permissions — reuses the existing Shizuku permission grant.
- Not addressing Bilibili-style multi-activity transitions (Kugou shows a single top activity, no `IntentHandlerActivity` → `UnitedBizDetailsActivity`-style chain that needs the +2s / +5s resize retries to handle — the existing retries already cover any such case generically).

## Decisions

### Decision 1: Constrain `am start` to a target package by adding `-p <pkg>` to the Shizuku command

`am start` accepts `-p <PACKAGE>` to restrict intent resolution to a single package. When set, the command behaves like `Intent.setPackage(<pkg>)` for `startActivity`: only intent-filters declared by that package are considered.

**Why this works for Kugou**:
- `https://m.kugou.com/mixsong/<id>.html` is registered as an intent-filter in both Kugou (`com.kugou.android`) and any installed browser. Without `-p`, HyperOS's resolver picks whichever has higher priority — typically the browser in user testing.
- With `-p com.kugou.android`, the resolver only considers Kugou's intent-filters; if Kugou is installed and the URL matches one of its filters, Kugou launches. If Kugou's filter doesn't match (e.g. wrong path pattern), `am start` exits non-zero and we fall back to the non-Shizuku path.

**Why it's safe for the other platforms**:
- `orpheus://song/<id>` is only declared by NetEase. Passing `-p com.netease.cloudmusic` is redundant but not harmful.
- Same for `qqmusic://` and `bilibili://`.
- The resolver behavior is unchanged on success; non-resolving cases produce the same exit-code-non-zero failure that today's no-`-p` invocation produces if the music app isn't installed.

**Alternatives considered**:
- **`-n <pkg>/<activity>`**: forces a specific component. Rejected: each music app's entry activity is internal and unstable (NetEase has `IconChangeDefaultAlias`, QQ Music has `SplashActivity` or similar). Hard-coding component names creates a fragile dependency on each app's internal manifest, while `-p` lets Android pick the right entry activity from the package's intent-filters.
- **Convert Kugou deep links to a custom scheme**: Kugou doesn't publish a working custom-scheme handler for arbitrary songs. The cerebrum-recorded experiments (`kugou://start.weixin?action=songinfo&hash=<hash>`) showed Kugou's `start.weixin` entry expects a URL-encoded JSON payload, not key=value params, and silently opens an unrelated song with the wrong format. Falling back to the HTTPS `_song_url` per song is the only reliable path.
- **`Intent.setPackage()` on a normal `startActivity` instead of Shizuku**: this is exactly what today's fallback path does, but loses freeform: a normal `startActivity` with `setPackage` ignores our `setLaunchWindowingMode(5)` reflective hint because non-system callers don't hold `MANAGE_ACTIVITY_TASKS` (cerebrum [2026-05-08]). Shizuku is the only path that achieves freeform.

### Decision 2: Derive target package from the deep link inside `launchFreeform`, not from a new parameter

`ShizukuLauncher.packageForDeepLink(deepLink)` already maps each known scheme/host to the target package and is used elsewhere by the resize watchdog. Reuse it inside `launchFreeform` to avoid adding a parallel argument that callers might forget to pass.

**Why**: keeps the call sites in `DeepLinkLauncher` and elsewhere unchanged; the launcher self-derives the package. Single source of truth for deep-link → package mapping.

**Trade-off**: `packageForDeepLink` returns `null` when the deep link doesn't match a known platform (e.g., a generic web URL). In that case `launchFreeform` SHALL omit the `-p` arg and behave exactly as today — `am start` falls back to the standard HTTPS resolver. This preserves any "unknown" use case without forcing callers to know the rule.

**Alternative considered**:
- Adding an explicit `targetPackage: String?` parameter to `launchFreeform`. Rejected: callers already work with deep links, and `packageForDeepLink` is the canonical mapping — duplicating the mapping at the caller risks drift (e.g., a new Kugou URL host gets added to `packageForDeepLink` but not to the caller's branch).

### Decision 3: Insert `-p` after `-d` in the existing argv, do not change other flags

The new command becomes:
```
am start --windowingMode 5 -a android.intent.action.VIEW -d <deepLink> [-p <pkg>] -f 0x10010000
```

The `-f 0x10010000` (FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_NO_ANIMATION) stays. The cerebrum-recorded ban on `FLAG_ACTIVITY_SINGLE_TOP` (0x20000000) [2026-05-10] stays. `--no-window-animation` is still excluded (HyperOS's `am` rejects it).

**Why no other flag changes**: every other piece of the freeform command was selected after specific failures (cerebrum notes [2026-05-08] / [2026-05-10]) — they're load-bearing and should not be revisited as part of this change.

### Decision 4: Locked-screen path and Shizuku-unavailable fallback remain unchanged

`launchForLockedScreen` and the fallback branch in `launchBackground` already set `setPackage(KUGOU_PACKAGE)` for Kugou URLs. No edit required — those paths use `startActivity`, where `setPackage()` already constrains resolution the same way `-p` does for `am start`. The "freeform doesn't render under keyguard" rationale in `DeepLinkLauncher.launch` ensures locked-screen still bypasses background mode entirely.

## Risks / Trade-offs

- **[Risk]** Passing `-p` to `am start` for an HTTPS URL whose package doesn't have a matching intent-filter on this device (e.g., Kugou Lite or an older Kugou version that doesn't claim `m.kugou.com/mixsong/<id>.html`) → `am start` exits non-zero and `launchFreeform` returns false.
  → **Mitigation**: `DeepLinkLauncher.launchBackground` already falls back to a regular Intent launch with `setPackage(KUGOU_PACKAGE)` + freeform-bundle hint when `launchFreeform` returns false. Same code path as Shizuku-not-installed: surfaces a Toast and continues to play (foregrounded, not freeform).

- **[Risk]** A newer Kugou version changes its intent-filter so neither `https://m.kugou.com/mixsong/<id>.html` nor `https://m.kugou.com/song/?hash=<hash>` is claimed → Kugou never opens.
  → **Mitigation**: log the non-zero `am start` exit code (already logged), and `launchBackground` already falls back to the browser via `launchFallback(fallbackUrl)`. Not regressed by this change — same failure mode exists today minus the wrong-app launch.

- **[Risk]** `packageForDeepLink` returns the wrong package for some future URL (e.g., a redirect host not in the regex) → `am start -p <wrong-pkg>` silently fails because the wrong app doesn't claim that URL.
  → **Mitigation**: failure is loud (`am` exit != 0, logged as `Shizuku am start exit=$exit`) and reverts to fallback path. Test plan covers each platform's canonical deep link shape.

- **[Trade-off]** `-p` adds two argv entries per launch (~negligible IPC cost; the call is already shelling out via Shizuku binder).

## Migration Plan

Single-PR change, no migration required:
1. Edit `ShizukuLauncher.launchFreeform` to resolve target package and conditionally insert `-p <pkg>` into the `am start` argv.
2. Build (`pixi run build`) and deploy (`pixi run deploy-release`).
3. Manual verification on device: queue a NetEase song, a QQ Music song, a Bilibili song, and a Kugou song in turn under `launch_mode=background`. All four SHALL open as off-screen freeform tasks; only Kugou's behavior is expected to change from "wrong app / fullscreen browser" to "Kugou in off-screen freeform."

No rollback needed beyond reverting the commit — the change is a pure addition to the `am start` argv, no settings/db migrations.
